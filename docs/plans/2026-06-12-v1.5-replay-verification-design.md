# V1.5 Replay And Verification Design

Docs/design plan for PR16. This document specifies the intended V1.5 replay and verification behavior without implementing it.

## 1. Scope

- Design only.
- MVP-only replay and verification first.
- No runtime code.
- No changes to `src/`, `tests/`, `package.json`, `CORE_VERSION`, package exports, tags or releases.
- No replay claim beyond the behavior specified here.

This design starts from the v0.1.0 MVP boundary: structured input, `norma.basic-proportions@0.1.0`, `surface-basic-third-grid`, construction, measurements, evaluation, comparison, explanation, derived artifacts, `Run`, `PackLock`, `OperationContext`, output refs and replay-readiness.

## 2. `replayRun`

`replayRun` should reproduce an MVP run from structured source truth and compare the replayed result to the recorded run envelope. It must not treat artifacts as source truth.

### Inputs

- Recorded `Run`, including `RunInput`, `RunOutput`, `runRef`, output refs, diagnostics and provenance.
- Structured source objects referenced by the run:
  - geometry input;
  - pack or pack source needed to recreate the effective `PackLock`;
  - resolved rule set or the source refs needed to resolve it again;
  - compositions;
  - evaluation profile;
  - comparison or tie policy when applicable.
- Effective `PackLock`.
- Effective `OperationContext`.
- Requested replay target, limited to the MVP truth path or one explicitly supported MVP operation.
- Optional strictness policy for diagnostic comparison and warnings handling.

### Outputs

- A structured replay result envelope.
- Recomputed output refs.
- Replay diagnostics.
- Mismatch list.
- Replay status.
- References to the original run and replayed run attempt.

### Supported MVP-only Cases

Initial replay support should be limited to the deterministic MVP truth path documented by the demo harness:

- validate explicit rectangular surface input;
- lock `norma.basic-proportions@0.1.0`;
- create the effective operation context;
- resolve `surface-basic-third-grid`;
- generate construction;
- measure MVP A/B compositions;
- evaluate A/B with `basic-grid-alignment`;
- compare the two evaluations in the same context;
- derive explanation and artifacts;
- wrap the replayed result in a run envelope.

Narrow single-operation replay may be designed later only when the public operation boundary is stable.

### What Gets Recomputed

- Effective pack lock from the supplied pack source.
- Effective operation context from explicit policies.
- Rule resolution.
- Construction.
- Measurements.
- Evaluations.
- Comparison, decision and explanation.
- Derived artifacts only from recomputed source objects.
- Run envelope and deterministic output refs.

### What Must Match

- Operation identity and operation version.
- Pack id, pack version, schema version and content identity.
- Geometry model, coordinate policy, metric policy and tolerance policy.
- Feature flags and other output-changing context.
- Source refs required by the run.
- Deterministic output refs.
- Statuses, blocking errors and critical warnings.
- Recomputed source-object content within the declared deterministic serialization boundary.

Non-critical warning order should match after canonical ordering is applied. Human-readable diagnostic text should be stable enough for review, but diagnostic code, severity, blocking status, target refs and provenance are the stronger contract.

### Mismatch Statuses

Allowed replay statuses:

- `replayed`: all required replay checks match.
- `replayed_with_warnings`: replay succeeded, with non-critical warning differences or explicitly tolerated review warnings.
- `mismatch`: replay completed but required deterministic content, refs, status, diagnostics or context differ.
- `non_replayable`: required source truth, pack lock, operation context, operation version or provenance is missing.
- `unsupported`: the run asks for behavior outside the MVP replay surface.
- `error`: replay could not complete because of invalid inputs or blocking diagnostics.

### Deterministic Output Expectations

- Same structured source truth plus same pack, rules, tolerances, operation version and context must produce the same replayed output.
- Timestamp metadata must not participate in deterministic identity.
- Output refs must be de-duplicated and ordered by the runtime ordering policy.
- Derived artifacts must be regenerated from source objects; they must not be copied forward as proof.

## 3. `verifyRun`

`verifyRun` should inspect whether a recorded run is complete, coherent and eligible for replay or audit. It may call `replayRun` later, but the verification contract should be useful without requiring replay execution.

### Verification Inputs

- `Run`.
- Referenced `PackLock`.
- Referenced `OperationContext`.
- Available source refs and source objects.
- Available output refs.
- Optional expected operation and operation version.
- Optional verification policy for warning strictness.

### Verification Outputs

- Verification status.
- Structured diagnostics.
- Missing dependency list.
- Context mismatch list.
- Source ref and output ref validation results.
- Artifact freshness summary when artifacts are present.
- Replay eligibility summary.

### Relation To Run, PackLock, OperationContext And OutputRefs

- `Run` is the verification subject.
- `PackLock` proves the effective pack identity used by the run.
- `OperationContext` proves output-changing context, including geometry model, coordinate policy, metric policy, tolerance policy, rounding, numeric behavior, ordering policy and feature flags.
- `outputRefs` identify deterministic outputs; they must not replace the actual structured output or source truth.
- A run that lacks required refs may still be inspectable, but it cannot be claimed replayable.

### Allowed Statuses

- `verified`: required run, lock, context, refs, diagnostics and source dependencies are coherent.
- `verified_with_warnings`: verification passes with non-blocking warnings.
- `mismatch`: required refs, lock, context, diagnostics or source dependencies conflict.
- `non_replayable`: required replay dependencies are absent or insufficient.
- `unsupported`: the run is outside the MVP verification surface.
- `invalid`: the run envelope or referenced runtime objects are malformed.

### Error And Warning Behavior

- Blocking errors remain blocking.
- Critical warnings cannot be suppressed.
- Missing source truth must be explicit.
- Diagnostic code, severity, blocking flag, target refs and provenance must stay visible.
- Verification must not convert missing information into success.

## 4. `verifyArtifactFreshness`

`verifyArtifactFreshness` should determine whether an artifact is still a trustworthy derived projection of current source objects. It must never promote an artifact into source truth.

### Artifact Inputs

- Artifact value.
- Artifact type.
- Artifact status when present.
- Artifact source refs.
- Artifact provenance.
- Artifact run ref when present.
- Artifact options that affect output.
- Available source objects.
- Available run, pack lock and operation context when needed.

### Source Refs

Source refs must point to structured Norma source objects such as geometry input, construction, measurements, evaluations, comparison, decision, explanation, `Run`, `PackLock` or `OperationContext`. Artifact refs may be used for traceability, but not as source proof for core truth.

### Freshness Behavior

Allowed artifact freshness statuses:

- `current`: source refs exist and match the artifact provenance and options.
- `lossy`: the artifact is current but intentionally omits detail or uses a lossy projection.
- `stale`: required source refs exist but no longer match the artifact provenance, options, output refs or run context.
- `non_replayable`: required run refs, source refs or provenance are missing, so freshness cannot be proven.
- `invalid`: the artifact shape is malformed or attempts artifact-as-source behavior.

An artifact can be useful for display or review while `lossy` or `non_replayable`, but those statuses must remain visible.

### Artifact Source Of Truth Rule

- Artifact content must never become geometry, pack, rule, measurement, evaluation, decision, explanation or run source truth.
- Regeneration must start from structured source objects.
- Modified artifacts do not mutate source objects.
- Artifact mismatch requires regeneration or warning, not source-object mutation.

## 5. Stable Serialization Boundary

The stable serialization boundary should define what future replay, verification and snapshots compare. PR16 does not freeze the final public JSON schema.

### Must Be Serialized

- Operation identity and operation version.
- Structured inputs.
- Pack identity and content identity through `PackLock`.
- Operation context policies that can influence output.
- Source refs and output refs.
- Result status.
- Structured warnings and errors.
- Provenance.
- Deterministic source outputs for the MVP truth path.
- Artifact metadata, source refs, options, status and provenance when artifacts are verified.

### Must Not Be Serialized As Deterministic Truth

- Wall-clock timestamps.
- Local file paths unless explicitly declared as source refs in a future reviewed boundary.
- Environment-specific absolute paths.
- Object insertion order from host runtime behavior.
- Presentation-only UI state.
- Artifact content as source truth.
- Unreviewed adapter, CLI, SDK, API or MCP wrapper fields.

### Ordering Policy

- Arrays with semantic order preserve that order.
- Sets, refs, diagnostics and output refs use canonical deterministic ordering.
- Duplicate refs are removed only when the runtime contract already treats them as duplicates.
- Ordering rules must be explicit before snapshots are treated as golden.

### Timestamp Policy

- Timestamps may exist as audit metadata.
- Timestamps must not participate in run identity, output refs or deterministic replay comparison.
- Snapshot tests should ignore or normalize timestamps.

### Deterministic Identity Policy

- Identity is derived from explicit structured dependencies, not from creation time.
- Pack content identity, operation version, operation context and source refs are identity inputs.
- Generated ids and output refs must be stable for the same deterministic inputs.
- To verify: whether future PR17 should define exact canonical JSON and hashing rules.

## 6. Fixtures And Golden Snapshots

### Needed Fixtures

- MVP truth path fixture matching `Surface proportionnelle évaluée`.
- Missing pack lock negative case.
- Missing evaluation profile negative case.
- Different comparison tolerance negative case.
- Blocked score output request negative case.
- Ratio absent from pack negative case.
- Missing rule negative case.
- Implicit pack rejection negative case.
- Context mismatch negative case.
- Artifact-as-source rejection negative case.
- Stale artifact case.
- Non-replayable artifact case.

### Golden Snapshot Coverage

- `PackLock`.
- `OperationContext`.
- Resolved rule set.
- Construction.
- Measurements A/B.
- Evaluations A/B.
- Comparison, decision and explanation.
- Derived artifact metadata and freshness status.
- Run envelope.
- Output refs.
- Replay or verification result envelopes once implemented.

### Must Remain Stable

- Diagnostic codes and severities.
- Blocking/non-blocking behavior.
- Replay and verification statuses.
- Output refs.
- Source refs.
- Pack lock identity fields.
- Operation context output-changing fields.
- Deterministic source-object structure.

### Snapshot Review Triggers

- Operation version change.
- Pack content identity change.
- Serialization boundary change.
- Diagnostic code, severity or blocking behavior change.
- Output ref policy change.
- Operation context policy change.
- Any intentional deterministic output change.

Snapshot changes should be reviewed as contract changes, not accepted as incidental churn.

## 7. Non-goals

- No CLI.
- No SDK.
- No API.
- No MCP.
- No adapter.
- No UI.
- No camera, image or vision.
- No CAD.
- No cloud.
- No beauty score.
- No creative recommendation.
- No runtime replay implementation.
- No engine modification.
- No final public JSON schema freeze.
- No tag or release.

## 8. Acceptance Criteria

- A reviewer can implement PR17 or PR18 from this design without guessing the intended replay and verification boundary.
- No runtime behavior is changed.
- No public CLI, SDK, API, MCP or adapter interface is frozen prematurely.
- Replay claims are precise and not overclaimed.
- Artifact freshness preserves the rule that artifacts are derived and never source truth.
- Unverified serialization details are marked to verify instead of guessed.
- The diff adds only this document.
