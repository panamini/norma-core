# Norma Core V1.5 Implementation Contracts

Documentation-only final contract bundle for Norma Core V1.5 before runtime implementation.

This document consolidates the remaining V1.5 design decisions after:

- the `v0.1.0` MVP checkpoint;
- PR15 V1.5 planning;
- PR16 replay and verification design.

It is intentionally the last broad docs-only V1.5 planning document before runtime PRs begin. Later docs may accompany runtime PRs, but they should not reopen the whole V1.5 design.

## 1. Scope

### In scope

This document defines the final pre-runtime contracts for:

- PR16 ambiguity resolutions;
- `verifyRun` / `replayRun` status mapping;
- pack source versus effective `PackLock` precedence;
- canonical serialization and deterministic identity policy;
- public operation call/result boundary;
- V1.5 serialization boundary;
- deterministic fixtures and golden snapshots;
- package, SDK, CLI and MCP readiness gates;
- runtime implementation sequence after this document.

### Out of scope

This document does not implement runtime behavior.

This document does not:

- modify `src/`;
- modify `tests/`;
- modify `package.json`;
- modify `package-lock.json`;
- modify `CORE_VERSION`;
- create CLI;
- create SDK;
- create API;
- create MCP;
- create adapter;
- create plugin;
- create tag;
- create release;
- reopen the MVP;
- change the `v0.1.0` checkpoint.

### Design posture

V1.5 should move from replay-readiness to operational replay and verification without turning external surfaces into source truth.

The correct build order is:

1. stable serialization and canonical ordering;
2. deterministic fixtures and golden snapshots;
3. artifact freshness verification;
4. run verification;
5. MVP-only replay;
6. package/SDK consumption;
7. thin CLI;
8. MCP only after tool contracts are reviewed.

CLI, SDK and MCP must consume stable contracts. They must not define Norma truth.

## 2. PR16 ambiguity resolutions

PR16 intentionally left three implementation-sensitive questions to resolve before runtime work:

1. how `verifyRun` statuses map to `replayRun` statuses;
2. precedence between supplied pack source and recorded/effective `PackLock`;
3. canonical JSON, hashing and deterministic identity policy.

This section resolves those questions for V1.5.

## 3. `verifyRun` and `replayRun` status mapping

### Status sets

`replayRun` statuses are:

- `replayed`;
- `replayed_with_warnings`;
- `mismatch`;
- `non_replayable`;
- `unsupported`;
- `error`.

`verifyRun` statuses are:

- `verified`;
- `verified_with_warnings`;
- `mismatch`;
- `non_replayable`;
- `unsupported`;
- `invalid`.

These statuses are not identical because the operations answer different questions.

`verifyRun` answers:

> Is this recorded run coherent, complete enough for the requested verification policy, and eligible for replay or audit?

`replayRun` answers:

> Can this run be recomputed from structured source truth, and does the recomputed result match the recorded run?

### Verification modes

`verifyRun` should support explicit verification modes.

| Mode | Meaning | Replay execution |
|---|---|---|
| `audit_only` | Validate the run envelope, refs, diagnostics, `PackLock`, `OperationContext`, source refs and replay eligibility without executing replay. | No |
| `replay_eligible` | Validate the run and require that all dependencies needed for later replay are present. | No |
| `replay_required` | Validate the run and execute or require a replay result. | Yes, once `replayRun` exists |

Initial V1.5 implementation should start with `audit_only` and `replay_eligible`. `replay_required` should be added only after `replayRun` exists.

### Mapping when replay is not executed

When `verifyRun` does not execute replay, it must not claim that replay succeeded.

| Condition | `verifyRun` status | Replay eligibility |
|---|---|---|
| Run, refs, lock, context and required source refs are coherent. | `verified` | `eligible` or `not_requested` |
| Run is coherent but has non-blocking warnings, missing optional artifacts, or non-critical diagnostic differences. | `verified_with_warnings` | `eligible`, `not_eligible`, or `not_requested` |
| Required run refs, lock fields, context fields, diagnostics or source dependencies conflict. | `mismatch` | `not_eligible` |
| Required replay dependencies are absent under `replay_eligible` mode. | `non_replayable` | `not_eligible` |
| Operation is outside the V1.5 verification surface. | `unsupported` | `unsupported` |
| Run envelope, `PackLock`, `OperationContext`, diagnostics or refs are malformed. | `invalid` | `unknown` |

A `verified` result without replay execution means “coherent by inspection,” not “replayed.”

### Mapping when replay is executed

When `verifyRun` executes or consumes a `replayRun` result, the mapping is:

| `replayRun` status | `verifyRun` status | Notes |
|---|---|---|
| `replayed` | `verified` | Static verification must also pass. |
| `replayed_with_warnings` | `verified_with_warnings` | Warnings remain visible. |
| `mismatch` | `mismatch` | Replay mismatch is verification mismatch. |
| `non_replayable` | `non_replayable` | Missing replay dependencies remain explicit. |
| `unsupported` | `unsupported` | Unsupported replay target remains unsupported verification. |
| `error` | `invalid` or `mismatch` | Use `invalid` for malformed input/envelope; use `mismatch` for completed replay that produced conflicting output. |

`verifyRun` must preserve the original replay status in a `replaySummary` or equivalent field. It must not collapse replay detail into a generic success/failure boolean.

### Required `verifyRun` replay summary fields

When replay is considered, `verifyRun` should expose:

- `replayAttempted: boolean`;
- `replayRequired: boolean`;
- `replayEligible: "eligible" | "not_eligible" | "not_requested" | "unsupported" | "unknown"`;
- `replayStatus` when a replay result exists;
- `replayDiagnostics`;
- `replayMismatches`;
- `replayOutputRefs`;
- `recordedOutputRefs`;
- `sourceRefsUsed`.

This keeps verification and replay separate while allowing reviewers to see how they relate.

## 4. Pack source and `PackLock` precedence

### Core rule

For replay and verification, structured source truth wins over derived or recorded projections.

A `PackLock` is the recorded effective identity of the pack used by a run. It proves what pack identity, version, schema version and content identity the run claims to have used.

The pack source is the structured pack content used to recompute or verify that identity.

### Precedence model

V1.5 should use this precedence model:

1. The recorded `PackLock` is the expected pack identity for the run.
2. The supplied pack source is the recomputation source for verifying or rebuilding the effective lock.
3. The recomputed lock from the supplied pack source must match the recorded `PackLock`.
4. If the supplied pack source and recorded `PackLock` disagree, the result is `mismatch`.
5. If the recorded `PackLock` is missing and replay requires it, the result is `non_replayable`.
6. If the supplied pack source is missing and replay requires recomputation, the result is `non_replayable`.
7. If the supplied pack source is malformed, the result is `invalid` for `verifyRun` or `error` for `replayRun`.
8. A client, adapter, CLI, SDK, MCP tool or agent must not silently replace the recorded `PackLock`.

### Required checks

`verifyRun` and `replayRun` must check at least:

- pack id;
- pack version;
- pack schema version;
- pack content identity;
- required ratio refs;
- required rule refs;
- declared rule set identity;
- effective pack source refs when available;
- provenance for pack-derived outputs.

### Allowed outcomes

| Case | `verifyRun` | `replayRun` |
|---|---|---|
| Recorded lock matches recomputed lock. | `verified` or `verified_with_warnings` | `replayed` or `replayed_with_warnings` |
| Recorded lock conflicts with recomputed lock. | `mismatch` | `mismatch` |
| Recorded lock missing. | `non_replayable` | `non_replayable` |
| Pack source missing when recomputation is required. | `non_replayable` | `non_replayable` |
| Pack source malformed. | `invalid` | `error` |
| Pack is outside supported MVP replay surface. | `unsupported` | `unsupported` |

### No silent fallback

V1.5 must not silently fall back to:

- a default pack;
- the current package’s embedded MVP pack;
- a pack selected by CLI;
- a pack selected by SDK;
- a pack selected by MCP;
- a pack inferred from artifact contents;
- a pack inferred from prompt text.

Missing pack or lock information must remain visible as diagnostics.

## 5. Canonical JSON, hashing and deterministic identity

### Decision

Canonical JSON is in V1.5 scope as a deterministic serialization policy.

Cryptographic hashing is not required for the first V1.5 runtime implementation unless a later PR explicitly approves it.

V1.5 should first implement deterministic canonical serialization and stable comparison. Hashing may be layered later on top of the canonical representation.

### Reason

The immediate V1.5 need is to compare runs, artifacts and golden snapshots deterministically.

That requires:

- stable object key ordering;
- stable ref ordering;
- stable diagnostic ordering;
- stable output ref ordering;
- timestamp exclusion or normalization;
- explicit handling of optional and undefined fields;
- repeatable serialization across runs.

It does not require committing to a final cryptographic content-addressing scheme in the first runtime PR.

### Canonical JSON policy

V1.5 canonical JSON should follow these rules:

- Object keys are serialized in lexicographic order.
- Arrays with semantic order preserve their declared order.
- Arrays that represent unordered refs, diagnostics or output refs use explicit canonical ordering.
- `undefined` values are omitted.
- `null` values are preserved only when they are semantically meaningful.
- Numbers are serialized using the runtime’s stable JSON number representation, with additional numeric normalization deferred unless a concrete mismatch is found.
- Strings are preserved exactly.
- Booleans are preserved exactly.
- Timestamps are excluded from deterministic identity unless explicitly marked as deterministic source fields.
- Environment-specific absolute paths are excluded from deterministic identity.
- Presentation-only fields are excluded from deterministic identity.
- Artifact content is never serialized as source truth.

### Hashing policy

V1.5 should define hash fields only as optional future metadata.

Initial V1.5 runtime PRs should not require a cryptographic hash.

Allowed in initial V1.5:

- `canonicalJson` or equivalent deterministic serialized form for tests and snapshot comparison;
- deterministic identity inputs documented and compared directly;
- optional placeholder fields marked as not authoritative.

Deferred unless explicitly approved:

- cryptographic hash algorithm selection;
- content-addressed storage;
- signature verification;
- remote registry identity;
- package distribution hash guarantees;
- final public hash schema.

### Deterministic identity inputs

Deterministic identity may include:

- operation id;
- operation version;
- geometry model version;
- pack id;
- pack version;
- pack schema version;
- pack content identity;
- rule set ref;
- evaluation profile ref;
- tolerance policy;
- coordinate policy;
- metric policy;
- ordering policy;
- numeric policy;
- feature flags that affect output;
- source refs;
- deterministic output refs;
- structured diagnostics that affect validity or replayability.

Deterministic identity must not include:

- wall-clock timestamps;
- local absolute paths;
- machine-specific environment values;
- non-deterministic object insertion order;
- UI state;
- display-only artifact fields;
- prompt text;
- adapter-private state;
- MCP-private state;
- CLI invocation text unless explicitly normalized as operation input in a later approved boundary.

### To verify during PR18

PR18 should verify against active code:

- current output ref ordering behavior;
- existing `OperationContext` ordering policy fields;
- current handling of timestamps in `Run`;
- current artifact status fields;
- current diagnostic ordering behavior;
- current `CORE_VERSION` and operation version fields.

PR18 should not invent behavior that contradicts active runtime contracts.

## 6. Public operation boundary

### Goal

The V1.5 public operation boundary should make runtime calls stable enough for thin clients without freezing a broad SDK, CLI, API or MCP contract too early.

The public boundary defines the shape of an operation call and operation result. It does not imply that all operations are public immediately.

### Operation call shape

A V1.5 operation call should include:

- `operation`;
- `operationVersion`;
- `input`;
- `operationContext`;
- `packLock` when a pack influences output;
- `sourceRefs`;
- `requestedOutputs`;
- `requestedArtifacts`;
- `validationLevel`;
- `strictness`;
- `featureFlags`;
- `metadata`.

### Operation call field policy

| Field | Required? | Notes |
|---|---:|---|
| `operation` | Yes | Must be explicit. No implicit operation selection. |
| `operationVersion` | Yes | Output-changing behavior must be versioned. |
| `input` | Yes | Must be structured. No prompt-as-source. |
| `operationContext` | Yes when output-changing context exists | Hidden defaults are forbidden. |
| `packLock` | Yes when a pack influences output | Missing pack/lock is an error or non-replayable condition. |
| `sourceRefs` | Yes when derived output is requested | Required for provenance. |
| `requestedOutputs` | Optional | Must not request forbidden output. |
| `requestedArtifacts` | Optional | Artifacts remain derived. |
| `validationLevel` | Optional with explicit default | Default must be documented. |
| `strictness` | Optional with explicit default | Used for replay/verification comparison. |
| `featureFlags` | Optional with explicit default | Output-changing flags must be visible. |
| `metadata` | Optional | Must not affect deterministic output unless explicitly declared. |

### Operation result shape

A V1.5 operation result should include:

- `status`;
- `output`;
- `outputRefs`;
- `warnings`;
- `errors`;
- `provenance`;
- `runRef`;
- `packLockRef`;
- `operationContextRef`;
- `diagnosticsSummary`;
- `serializationSummary` when deterministic serialization is used;
- operation-specific summary fields when appropriate.

### Result status policy

Operation results must avoid generic booleans as primary status.

Statuses should be operation-specific but compatible with the existing `CoreResult` style.

Result statuses must distinguish:

- successful execution;
- successful execution with warnings;
- invalid input;
- unsupported operation;
- mismatch;
- non-replayable state;
- stale artifact;
- forbidden source behavior;
- blocking diagnostic failure.

### Diagnostics

Diagnostics must include:

- code;
- severity;
- message;
- target ref when available;
- source;
- blocking flag;
- provenance when available.

Diagnostic text can be human-readable, but diagnostic code, severity, blocking flag, target ref and provenance are the stronger contract.

### Provenance

Derived output must preserve provenance.

Provenance should identify:

- input source;
- pack source;
- rule source;
- operation source;
- operation version;
- context source;
- measurement source where relevant;
- evaluation source where relevant;
- artifact source refs where relevant.

A derived output without required provenance must be rejected or marked with a critical warning according to the operation contract.

### Refs

Refs are not source truth by themselves. They connect objects and preserve traceability.

V1.5 should use refs for:

- run identity;
- pack lock identity;
- operation context identity;
- output identity;
- source object identity;
- artifact source refs;
- diagnostic target refs.

Refs must not replace required structured source objects during replay.

## 8. Stable serialization contract

### Serialization categories

V1.5 serialization should classify data into these categories:

1. deterministic source truth;
2. deterministic derived output;
3. deterministic diagnostics;
4. deterministic refs;
5. non-deterministic metadata;
6. presentation-only metadata;
7. external client metadata.

Only categories 1 through 4 participate in replay comparison and golden snapshots by default.

### Source objects

Source objects may include:

- structured geometry input;
- ratio pack source;
- rule declarations from packs;
- resolved rule set;
- construction;
- measurements;
- evaluations;
- comparison;
- decision;
- explanation;
- `Run`;
- `PackLock`;
- `OperationContext`.

Artifacts are not source objects for core truth.

### Derived objects

Derived objects may include:

- structured result artifacts;
- construction summary artifacts;
- evaluation report artifacts;
- explanation artifacts;
- simple visual artifacts;
- CSV measurement exports if later approved;
- adapter reports if later approved.

Derived objects must:

- preserve source refs;
- preserve warnings and errors;
- preserve provenance;
- carry freshness or replayability status when relevant;
- never become source truth.

### Excluded fields

The serialization boundary excludes from deterministic identity:

- wall-clock timestamps;
- local absolute file paths;
- host-specific environment values;
- random ids;
- object insertion order;
- UI presentation state;
- display-only hints;
- artifact rendering content as source truth;
- adapter-private fields;
- MCP-private fields;
- CLI-private invocation metadata;
- free-form prompt text.

### Ordering

Canonical ordering should be explicit:

- object keys: lexicographic;
- output refs: runtime deterministic ordering policy;
- diagnostics: by severity, blocking flag, code, target ref, source and stable message fallback;
- source refs: lexicographic by ref id unless semantic order is declared;
- artifact refs: lexicographic by artifact id or source ref;
- warnings and errors: canonical diagnostic ordering;
- arrays with semantic meaning: preserve semantic order.

### Timestamp policy

Timestamps may exist as audit metadata.

Timestamps must not affect:

- deterministic identity;
- output refs;
- replay comparison;
- golden snapshot identity;
- canonical hash if hashing is later introduced.

Snapshot tests should omit, normalize or separately assert timestamp metadata.

### Numeric policy

V1.5 should not introduce broad numeric normalization unless current runtime behavior requires it.

Initial policy:

- preserve existing numeric outputs;
- compare exact serialized numbers where the current runtime is deterministic;
- if numeric instability is found, introduce a documented numeric comparison policy in the relevant runtime PR;
- do not hide tolerance changes;
- do not round values silently if rounding changes output.

### Serialization summary

Operations that use canonical serialization should expose a summary such as:

- serialization version;
- canonical ordering policy id;
- timestamp policy id;
- deterministic fields included;
- deterministic fields excluded;
- warnings if excluded fields were present;
- to verify: exact field names should be aligned to active code in PR18.

## 9. Compatibility and versioning policy

### Operation version

An operation version must change when output-changing behavior changes.

Requires operation version review:

- changed deterministic output structure;
- changed diagnostic codes;
- changed blocking behavior;
- changed output ref generation;
- changed source ref requirements;
- changed tolerance behavior;
- changed ordering policy;
- changed replay status semantics;
- changed artifact freshness semantics.

Does not necessarily require operation version change:

- documentation clarification;
- non-deterministic metadata addition;
- purely internal refactor with identical serialized output;
- test-only fixture addition;
- non-blocking human-readable message wording change, if diagnostic code/severity/blocking/provenance remain unchanged.

### Serialization version

The serialization boundary should have an explicit version once implemented.

Serialization version should change when:

- canonical field inclusion changes;
- canonical ordering changes;
- timestamp inclusion/exclusion changes;
- diagnostic canonicalization changes;
- ref canonicalization changes;
- deterministic identity inputs change.

### Snapshot review

Golden snapshot changes are contract changes unless proven otherwise.

A snapshot update must explain:

- why the output changed;
- whether operation version changes;
- whether serialization version changes;
- whether diagnostic behavior changes;
- whether replay compatibility changes;
- whether the change is expected for existing runs.

## 10. Error and warning policy

### Blocking errors

Blocking errors remain blocking.

A replay, verification or serialization operation must not convert blocking errors into warnings.

### Critical warnings

Critical warnings cannot be suppressed by:

- UI;
- CLI;
- SDK;
- API;
- MCP;
- adapter;
- agent.

Critical warnings must remain visible in operation results and derived artifacts.

### Missing source

Missing required source truth must produce:

- `non_replayable` when the envelope is coherent but dependencies are absent;
- `invalid` when the envelope or refs are malformed;
- `mismatch` when available sources conflict with recorded refs;
- `unsupported` when the requested operation is outside the V1.5 surface.

### Unsupported operation

Unsupported operation should be explicit.

It must not fall back to:

- a similar operation;
- a default pack;
- a default profile;
- a default tolerance;
- an inferred rule;
- an agent-created rule.

### Stale artifact

A stale artifact means the artifact no longer matches its required source refs, provenance, options, output refs or run context.

A stale artifact must not mutate source objects.

The correct response is:

- report stale status;
- require regeneration from source truth;
- preserve diagnostics.

### Non-replayable run

A non-replayable run may still be useful for audit, but it must not be claimed replayable.

Reasons include:

- missing source refs;
- missing `PackLock`;
- missing `OperationContext`;
- missing operation version;
- unsupported operation;
- missing provenance;
- stale or insufficient artifacts;
- missing pack source when recomputation is required.

- stale artifact case;
- non-replayable artifact case;
- pack lock mismatch case;

### Required golden snapshots

Golden snapshots should cover:

- canonical `PackLock`;
- canonical `OperationContext`;
- resolved rule set;
- construction;
- measurements A/B;
- evaluations A/B;
- comparison;
- decision;
- explanation;
- derived artifact metadata;
- artifact freshness statuses;
- run envelope;
- deterministic output refs;
- `verifyArtifactFreshness` result envelope once implemented;
- `verifyRun` result envelope once implemented;
- `replayRun` result envelope once implemented.

### Snapshot structure

Snapshots should separate:

- deterministic source objects;
- deterministic derived outputs;
- diagnostics;
- refs;
- summaries;
- non-deterministic metadata.

This prevents timestamp or presentation churn from hiding meaningful contract changes.

### Must remain stable

The following must remain stable unless an explicit contract change is approved:

- diagnostic codes;
- diagnostic severities;
- blocking flags;
- replay statuses;
- verification statuses;
- artifact freshness statuses;
- output refs;
- source refs;
- pack lock identity fields;
- operation context output-changing fields;
- deterministic source-object structure;
- canonical ordering policy;
- serialization version.

### Snapshot review triggers

Snapshot updates require review when any of these changes:

- operation version;
- serialization version;
- pack content identity;
- diagnostic code;
- diagnostic severity;
- blocking behavior;
- output ref policy;
- source ref policy;
- ordering policy;
- operation context policy;
- artifact freshness behavior;
- replay status behavior;
- verification status behavior;
- deterministic output content.

Snapshot changes should not be accepted as incidental churn.

## 12. Package, SDK, CLI and MCP readiness

### Package readiness

Package work may begin only after:

- public operation boundary is accepted;
- stable serialization helpers are implemented;
- fixtures and snapshots exist;
- replay/verification statuses are stable enough for external consumption.

Package export review should avoid broad surface expansion.

### SDK consumption docs readiness

Minimal SDK consumption docs may explain how to call approved operations, but they must not invent an SDK runtime.

SDK docs may cover:

- operation call shape;
- operation result shape;
- diagnostics handling;
- provenance handling;
- replay/verification statuses;
- artifact freshness statuses.

SDK docs must not imply:

- broad public API stability;
- cloud API availability;
- adapter logic;
- creative recommendations;
- beauty scoring;
- prompt-as-source support.

### CLI readiness gate

A thin CLI can be considered only after:

- `verifyArtifactFreshness` exists;
- `verifyRun` exists;
- MVP-only `replayRun` exists or is explicitly not required for the CLI scope;
- serialization behavior is stable;
- golden snapshots cover CLI-relevant outputs;
- CLI output format is reviewed.

CLI must remain thin.

CLI must not:

- create packs;
- create ratios;
- create rules;
- infer tolerances;
- infer geometry from images;
- treat artifacts as source truth;
- hide warnings or errors;
- define Norma logic.

### MCP readiness gate

MCP must come after replay, verification and operation boundary stability.

MCP may be designed only after:

- tool contracts are reviewed;
- operation result envelopes are stable;
- diagnostics and provenance behavior are stable;
- agent limits are explicit;
- golden snapshots cover tool-relevant outputs.

MCP must not:

- create packs;
- create ratios;
- create rules;
- create tolerances;
- create geometry;
- infer design intent;
- produce beauty score;
- optimize creatively;
- treat artifacts as source truth;
- suppress critical warnings;
- hide errors;
- bypass operation contracts.

MCP tools should expose narrow calls to approved operations only.
